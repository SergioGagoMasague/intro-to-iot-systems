18  AI on IoT and Edge ML

TipLearning objectives

After this chapter you should be able to:

  1. Explain the limits of cloud-only processing for IoT, and place computation along the device–edge–cloud continuum.
  2. Describe Edge AI and TinyML, and give examples of where they are used.
  3. Review the supervised-learning concepts most used in IoT: classification, regression, features, training and testing.
  4. Explain why model size matters on microcontrollers, and how quantization and pruning shrink models.
  5. Follow the TinyML workflow from data collection to on-device inference.
  6. Evaluate an edge model on accuracy, latency, memory and energy.

18.1 Why it matters

IoT devices produce enormous volumes of raw data: accelerations sampled hundreds of times a second, audio, images, vibration spectra. The first generation of IoT systems sent all of it to the cloud for analysis. That works for a few devices with good connections, but it breaks down at scale, for battery-powered devices, and whenever a decision is needed immediately or the data is too sensitive to leave the device.

Advances in algorithms, model compression and microcontroller hardware now make it possible to run machine-learning models directly on devices like the ESP32. A smart doorbell can tell a person from a package without contacting a server; a wearable can detect a fall in milliseconds; a vibration sensor can flag a failing bearing and send one alert instead of streaming data all day. This chapter explains how.

18.2 Concepts

The limits of cloud-only processing

Sending all raw data to the cloud has four costs:

  • Latency. A round trip to the cloud takes tens to hundreds of milliseconds, and much longer on poor networks, too slow for emergency stops, fall detection or control loops.
  • Bandwidth. Streaming audio or video from many devices consumes network capacity and, on cellular links, money.
  • Energy. Transmitting data usually costs far more energy than processing it locally (Chapter 10).
  • Privacy. Raw data, such as audio from a living room, must leave the device, increasing the risk of leaks and misuse (Chapter 14).

There is also availability: a device that depends on the cloud to make every decision stops working when the network does.

The device–edge–cloud continuum

Computation can happen at several places between the sensor and the data center:

Fog computing describes the middle tier: computing, storage and networking resources between devices and the cloud, often virtualized and shared, close to where the data is produced. Real systems split work across tiers. A camera might detect motion on the device, identify objects at the edge, and train improved models in the cloud.

Edge AI and TinyML

Edge AI means running machine-learning models on devices or edge nodes instead of only in the cloud. Only the result (“person detected”, “fall”, “abnormal vibration”) needs to be sent. Its benefits are real-time response, offline operation, lower bandwidth and energy, and privacy.

TinyML is the part of Edge AI that runs on the smallest devices: microcontrollers with kilobytes of memory and milliwatts of power. It sits at the overlap of machine learning and embedded systems, and applies when rule-based logic is not enough but the device is too small for conventional ML.

Typical applications include:

  • keyword spotting (“Hey…”) in smart speakers, running continuously at very low power;
  • activity recognition and fall detection in wearables;
  • anomaly detection in industrial machines (predictive maintenance);
  • visual wake words (is there a person in the image?) in cameras and doorbells;
  • gesture recognition from IMUs.

A machine-learning refresher

Machine learning teaches a computer rules from data instead of hard-coding them. Instead of writing “if acceleration > X then running”, you collect labeled acceleration data and train a model that learns the boundary.

  • Supervised learning uses labeled examples. Classification predicts a category (walking or running); regression predicts a number (the temperature in an hour, a motor’s speed from its sound).
  • Unsupervised learning finds structure without labels, for example clustering, or anomaly detection: learning what “normal” looks like and flagging what is not.
  • Training adjusts the model’s parameters to reduce errors on labeled examples. Testing evaluates it on data it has never seen, to check that it generalizes rather than memorizing.

Common supervised models for edge IoT include:

Model Idea Edge suitability
k-nearest neighbors Predict from the labels of the most similar stored examples Simple, but must store training data
Decision trees and small forests A sequence of threshold tests Tiny, fast, interpretable; easy to export as code
Linear and logistic regression Weighted sum of features Tiny and fast
Neural networks (MLPs, 1D/2D CNNs, small RNNs) Layers of learned weights; CNNs capture spatial or temporal patterns Most powerful; need compression to fit

Features from sensor data

Raw sensor streams are usually turned into features before (or inside) a model. For time series, a common pipeline is:

  1. Windowing: split the stream into fixed-length windows, for example 2 s of accelerometer data at 50 Hz (100 samples), often overlapping.
  2. Feature extraction: compute summary statistics for each window and axis, such as mean, standard deviation, minimum, maximum, energy, zero crossings or the magnitudes of frequency components.
  3. Classification of each window.

Neural networks can learn their own features from raw windows, at the cost of more computation and data.

Why model size matters

A model that works in a notebook may be far too large for a microcontroller:

Cloud server ESP32
Memory Hundreds of GB of RAM 520 KB of SRAM (part used by Wi-Fi and the RTOS)
Storage Terabytes 4 MB of flash, shared with the firmware
Compute GPUs, TFLOPS Two 240 MHz cores, single-precision FPU
Power Hundreds of watts Tens to hundreds of milliwatts

Edge models must therefore be tiny and efficient, trading some accuracy for size and speed. The main compression techniques are:

  • Quantization: storing weights and activations as 8-bit integers instead of 32-bit floats. This makes models about four times smaller and much faster on hardware without a strong floating-point unit, usually with only a small loss of accuracy. Post-training quantization converts a trained model; quantization-aware training simulates quantization during training for better accuracy.
  • Pruning: removing weights or whole neurons that contribute little.
  • Knowledge distillation: training a small “student” model to imitate a large “teacher”.
  • Architecture choice: using small, efficient model families designed for embedded devices.

The TinyML toolchain

Tool Role
LiteRT for Microcontrollers (formerly TensorFlow Lite for Microcontrollers) The most widely used inference runtime for MCUs; runs quantized models converted from TensorFlow, Keras, PyTorch or JAX
Edge Impulse End-to-end platform: collect data from a device, label, train, optimize and generate firmware
ExecuTorch PyTorch’s lightweight runtime for edge and embedded devices
Vendor libraries Espressif ESP-DL, esp-tflite-micro and ESP-DSP; Arm CMSIS-NN; ST X-CUBE-AI; NXP eIQ. These use each chip’s accelerators and special instructions.

The typical workflow is:

  1. Collect and label data on the real device, in realistic conditions.
  2. Train a model on a PC, often in a Jupyter notebook.
  3. Optimize: quantize, prune, and check accuracy after each step.
  4. Convert to the runtime’s format (for LiteRT, a .tflite flat buffer, embedded in firmware as a C array).
  5. Deploy to the device and run inference on live data.
  6. Evaluate on the device: accuracy, latency, memory and energy, then iterate.

A tiny example: classifying motion with a decision tree

Not every edge model needs a neural network. A decision tree trained in Python (for example with scikit-learn) can be exported as plain C code. This one classifies 2-second accelerometer windows from the MPU-6050 (Chapter 6) as still, walking or running, using two features:

// Features computed over a 2 s window of acceleration magnitude (in g)
struct Features { float meanMag; float stdMag; };

Features extract(const float* mag, int n) {
  float sum = 0, sq = 0;
  for (int i = 0; i < n; i++) { sum += mag[i]; sq += mag[i] * mag[i]; }
  float mean = sum / n;
  return { mean, sqrtf(fmaxf(sq / n - mean * mean, 0.0f)) };
}

// Exported from a depth-2 decision tree (thresholds learned from labeled data)
const char* classify(const Features& f) {
  if (f.stdMag < 0.05f) return "still";
  if (f.stdMag < 0.45f) return "walking";
  return "running";
}

The whole model is a few comparisons and takes microseconds. The thresholds above are illustrative; yours must come from your own labeled data, collected on your kit and with the sensor mounted the way it will be used.

Evaluating an edge model

Accuracy alone does not decide whether a model is suitable for a device. Measure, on the device:

  • accuracy on held-out data collected separately from the training data, preferably from different people or machines; also precision and recall when classes are imbalanced;
  • latency per inference;
  • memory: flash for the model and code, RAM for activations (“tensor arena” in LiteRT);
  • energy per inference and per day, given how often inference runs.

Two practical risks recur:

  • Distribution shift. Models trained in the lab fail in the field when conditions differ: a different user, a different mounting position, a noisier machine.
  • Silent failure. A model always returns some answer. Monitoring confidence and occasionally sending samples for review helps detect when it has stopped working.

Larger models at the edge

More capable edge hardware runs much larger models. Camera boards such as the ESP-EYE run face and object detection with Espressif’s ESP-WHO framework. Gateways and single-board computers with neural accelerators run real-time vision, and even small language models, on premises. The same principles apply: move computation toward the data when latency, bandwidth, energy or privacy demand it.

TipTry it on your kit: from rules to a learned classifier
  1. Record 2-second windows of MPU-6050 data while standing still, walking and running, at least 30 windows of each. Stream them over the serial port to a CSV file.
  2. In a notebook, compute the mean and standard deviation of the acceleration magnitude per window, and train a small decision tree. Report its accuracy on windows recorded by a different team member.
  3. Export the tree as C code and run it on the kit, showing the predicted activity on the OLED.
  4. Measure the classification time with micros(), and the RAM used by your window buffer.
  5. Optional: train a small neural network on the same data, quantize it to int8, and run it with LiteRT for Microcontrollers. Compare accuracy, size and latency with the tree.

18.3 In depth (optional)

Optional, in-depth explanation. This section goes beyond the rest of the chapter into the math and physics behind it. Nothing later in the book depends on it; skip it on a first reading.

Fitting a model into a microcontroller

Sampling first. To capture motion up to frequency \(f_\text{max}\), the Nyquist criterion requires sampling at \(f_s > 2 f_\text{max}\). Human walking has most of its energy below about 3 Hz, and arm gestures below about 10–15 Hz, so 50 Hz accelerometer sampling is ample; sampling slower lets faster movements alias into false low-frequency patterns.

Features from raw axes. The acceleration magnitude

\[ |a| = \sqrt{a_x^2 + a_y^2 + a_z^2} \]

does not depend on how the device is oriented, which makes it a robust input for step counting. Over a window of \(W\) samples, simple features such as the mean, standard deviation and number of threshold crossings summarize the motion into a few numbers a small model can use.

Counting the work. A fully connected layer with \(n_\text{in}\) inputs and \(n_\text{out}\) outputs performs \(n_\text{in} \times n_\text{out}\) multiply-accumulate operations (MACs) and stores the same number of weights. A 2-D convolution producing an \(H \times W \times C_\text{out}\) output with \(K \times K\) kernels over \(C_\text{in}\) input channels performs

\[ \text{MACs} = H\,W\,C_\text{out}\,K^2\,C_\text{in} . \]

A gesture model with layers 300→32→16→4 needs \(9600 + 512 + 64 \approx 10\,200\) MACs and as many weights. At a few cycles per MAC on a 240 MHz core, inference takes well under a millisecond.

Quantization. Storing weights as 8-bit integers instead of 32-bit floats cuts memory four times and allows faster integer arithmetic. The common affine scheme maps a real value \(x\) to an integer \(q\) with a scale \(s\) and zero point \(z\):

\[ q = \operatorname{round}\left(\frac{x}{s}\right) + z, \qquad x \approx s\,(q - z), \]

with \(s = (x_\text{max} - x_\text{min})/255\) for int8. The rounding error is at most \(s/2\) per value; accuracy usually drops by around a percentage point or less if the model was trained or calibrated with quantization in mind, and can drop much more if it was not.

Energy per inference. Energy is power times time: a core at 30 mA and 3.3 V running a 1 ms inference uses about 0.1 mJ. Sending the raw 300-sample window over Wi-Fi instead (hundreds of bytes plus connection overhead) costs far more. That ratio, compute is cheap and radio is expensive, is the main argument for edge intelligence.

Exercise. Your model has 25 000 float32 weights. How much flash does it need before and after int8 quantization? Would it fit alongside a 1.2 MB application in one 1.9 MB OTA partition?

Sources for this section: (Jacob et al. 2018; Warden and Situnayake 2019).

18.4 Design trade-offs

Decision Considerations
Device vs. edge vs. cloud inference Latency, energy, privacy and offline operation versus model capability and ease of updating
Hand-crafted features vs. learned features Features plus small models are tiny and interpretable; neural networks need less feature design but more data and compute
Quantization Smaller and faster, with some accuracy loss
Updating models Models need OTA updates too (Chapter 16), and versioning alongside firmware

18.5 Common pitfalls

  • Testing on the training data, or on windows from the same recording, which overstates accuracy.
  • Collecting data in only one condition. Models fail on other users, placements or environments.
  • Ignoring RAM for activations. A model that fits in flash can still run out of RAM at inference time.
  • Measuring latency on a PC instead of on the device.
  • Using ML where a threshold would do. Start with the simplest model that meets the requirement.
  • Shipping without monitoring. Model accuracy degrades silently.
NoteAdvanced track

Federated learning. Instead of sending raw data to the cloud, devices can train locally and send only model updates, which a server aggregates. Read about federated averaging and explain what it protects and what it does not (model updates can still leak information).

Energy-aware inference. Design a cascade: a tiny, always-on model (such as a motion threshold) wakes a larger model only when needed. Estimate the energy saved compared with running the larger model continuously.

Benchmarks. MLPerf Tiny defines standard tasks (keyword spotting, visual wake words, image classification, anomaly detection) and reports accuracy, latency and energy on microcontrollers. Compare published results for two microcontroller families.
