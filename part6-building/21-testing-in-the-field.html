21  Testing in the Field

TipLearning objectives

After this chapter you should be able to:

  1. Explain why IoT systems need testing beyond unit tests and bench demos.
  2. Plan tests at several levels: unit, hardware-in-the-loop, integration, long-duration and field.
  3. Design and run a multi-day reliability test with clear metrics and logging.
  4. Conduct a field test in a realistic environment and report its results.
  5. Instrument a device so that failures can be diagnosed remotely.
  6. Prepare a robust final demonstration.

21.1 Why it matters

A device that works for five minutes on a desk has proven very little. In the field it will meet weak signals, crowded radio bands, power glitches, network outages, memory leaks that only appear after two days, sensors that drift, and users who press buttons in the wrong order. Many IoT failures appear only after hours or days, or only in a particular place.

Testing in IoT therefore has two dimensions that ordinary software testing often lacks: time and environment. This chapter explains how to test along both.

21.2 Concepts

Levels of testing

Each level catches problems the others miss. Unit tests are fast and cheap but know nothing about radios; field tests are realistic but slow and hard to repeat.

Designing for testability

Testing is much easier if the firmware is designed for it:

  • Separate logic from hardware. Put decision logic (state machines, thresholds, message formatting) in functions that take values and return results, so they can be tested on a laptop.
  • Log meaningfully. Every important event (boot, reset reason, connect, disconnect, error, command received) should be logged with a timestamp and enough context to diagnose it later (Chapter 4).
  • Report health. Publish a periodic heartbeat with uptime, free heap, firmware version, signal strength (RSSI), reconnect counts and last error. A missing heartbeat is itself a signal.
  • Record why the device restarted. esp_reset_reason() distinguishes power-on, software reset, watchdog timeouts, brownouts and crashes.
#include <esp_system.h>

const char* resetReasonText() {
  switch (esp_reset_reason()) {
    case ESP_RST_POWERON:  return "power-on";
    case ESP_RST_SW:       return "software";
    case ESP_RST_PANIC:    return "crash";
    case ESP_RST_INT_WDT:
    case ESP_RST_TASK_WDT:
    case ESP_RST_WDT:      return "watchdog";
    case ESP_RST_BROWNOUT: return "brownout";
    case ESP_RST_DEEPSLEEP:return "deep-sleep wake";
    default:               return "other";
  }
}

void publishHeartbeat() {
  char msg[160];
  snprintf(msg, sizeof msg,
           "{\"up_s\":%lu,\"heap\":%u,\"rssi\":%d,\"fw\":\"%s\",\"reset\":\"%s\",\"reconnects\":%u}",
           millis() / 1000, ESP.getFreeHeap(), WiFi.RSSI(), FIRMWARE_VERSION,
           resetReasonText(), reconnectCount);
  mqtt.publish(HEARTBEAT_TOPIC, msg);
}

Fault injection

Deliberately break things and watch what happens:

Fault Expected behavior to verify
Wi-Fi access point switched off for 10 minutes Device keeps sensing and acting locally; buffers or drops data as designed; reconnects automatically
Broker or server unreachable Back-off between retries; no crash; no battery drain from tight retry loops
Sensor unplugged or returning nonsense Plausibility checks reject bad data; actuator goes to its fail-safe state (Chapter 7)
Power cut during a write or an update Settings and firmware remain valid (Chapter 16)
Burst of commands or malformed messages Device rejects invalid input without crashing
Clock not yet synchronized Timestamps and certificate checks behave sensibly

Long-duration reliability testing

A reliability test runs the complete system, unattended, for an extended period, typically 24 to 72 hours, and measures how well it keeps working.

Plan it like an experiment:

  1. Define the configuration: firmware version, hardware, location, network, power source.
  2. Define the metrics and how each is measured:
    • uptime and the number and causes of resets;
    • message delivery ratio: messages received ÷ messages sent, using sequence numbers to count gaps;
    • latency distribution (median and 95th percentile), using timestamps;
    • reconnections and how long each outage lasted;
    • free heap over time (a steady decline indicates a memory leak);
    • power or battery voltage over time, if battery-powered;
    • application-specific correctness, such as sensor values within plausible ranges.
  3. Log everything to a place that survives the device: the broker and a back-end database, not just the serial port.
  4. Run it without touching it. Intervening invalidates the result; if you must, record what you did and when.
  5. Analyze and report: plots of each metric over time, a list of every incident with its cause, and what you changed as a result.

A simple sequence-number scheme makes message loss measurable:

RTC_DATA_ATTR uint32_t seq = 0;      // survives deep sleep; resets on power loss

void publishReading(float value) {
  char msg[96];
  snprintf(msg, sizeof msg, "{\"seq\":%lu,\"t_ms\":%lu,\"v\":%.2f}", ++seq, millis(), value);
  mqtt.publish(DATA_TOPIC, msg);
}
// On the server: delivery ratio = received / (max_seq - min_seq + 1), per boot

Expect the first long test to find problems. That is its purpose. Typical findings include memory leaks from repeated String concatenation, connections that never recover after a router restart, watchdog resets from blocking network calls, and TLS sessions that fail after the device’s clock drifts.

Field testing

A field test places the system where it will actually be used, with the people who will actually use it. It reveals problems no lab can: a wall that blocks the signal, a sensor that reads differently in sunlight, a user who misunderstands the display.

A useful field-test plan includes:

  • objectives: which requirements and risks the test addresses;
  • site and setup: where devices are placed, with photos and a map;
  • procedure: what testers and users do, and for how long;
  • data collected: logs, measurements, observations, user feedback;
  • safety and permissions: permission to install devices, electrical and physical safety, and the privacy of anyone whose data is collected (Chapter 14, Chapter 17).

Report the results honestly. A field test that shows the range is half what you expected is valuable, provided you explain what you learned and what you would change.

Preparing the final demonstration

A live demo is a small field test under pressure. Reduce the risk:

  • Have a rehearsed script with a clear story: the problem, the system, the evidence that it works.
  • Bring your own network if possible (a travel router), or confirm the venue’s network in advance.
  • Keep a backup: a recorded video of the system working and screenshots of dashboards and long-test results.
  • Charge everything, and bring spare cables.
  • Show evidence, not just features: the reliability plots and field-test results are often more convincing than the live demo.
TipTry it on your kit: a 72-hour reliability test
  1. Add a heartbeat and sequence-numbered data messages to your project firmware.
  2. Write a small script on a laptop or server that subscribes to your topics and stores every message with its arrival time.
  3. Run the complete system unattended for 72 hours.
  4. Produce plots of message delivery ratio per hour, latency, free heap and RSSI, and a table of every reset and disconnection with its cause.
  5. Write one page on what failed, why, and what you changed.

21.3 In depth (optional)

Optional, in-depth explanation. This section goes beyond the rest of the chapter into the math and physics behind it. Nothing later in the book depends on it; skip it on a first reading.

How much testing is enough?

Field tests produce numbers such as “no failures in 72 hours” or “997 of 1000 packets delivered”. Statistics tells you how much those numbers actually prove.

Zero failures is not zero failure rate. If a test of \(n\) independent trials sees no failures, the 95% upper confidence bound on the failure probability is approximately

\[ p_\text{upper} \approx \frac{3}{n} \qquad \text{(the "rule of three")}, \]

because \((1 - p)^n = 0.05\) gives \(p \approx -\ln(0.05)/n \approx 3/n\). 1000 successful packets show, with 95% confidence, a loss rate below 0.3%, not a loss rate of zero.

Mean time between failures from a short test. For failures that occur at a constant rate, a test of total duration \(T\) with no failures supports, at confidence \(C\),

\[ \text{MTBF} \ge \frac{T}{-\ln(1 - C)} . \]

A 72-hour run with no failures shows MTBF ≥ 72/3.0 ≈ 24 hours at 95% confidence. To claim a month, you would need about three months of failure-free device-hours, which is why teams test many devices in parallel: 30 kits for 72 hours give 2160 device-hours.

Estimating a rate with an interval. For \(x\) successes in \(n\) trials, the observed rate is \(\hat p = x/n\), and a simple 95% interval is

\[ \hat p \pm 1.96\sqrt{\frac{\hat p (1 - \hat p)}{n}} . \]

997 of 1000 gives 99.7% ± 0.34%. The approximation is poor near 0% and 100%, where the Wilson interval is better, but it shows the key point: to halve the uncertainty, you need four times the trials.

Comparing before and after. If a fix raises delivery from 96% to 98%, is that real? With 200 packets each, the intervals (about ±2.7% and ±1.9%) overlap; with 2000 each they do not. Decide the sample size before the test, not after seeing the result.

Exercise. Your team’s device must deliver at least 99% of readings. How many consecutive successful readings, with no failures, would let you claim that with 95% confidence?

Sources for this section: (Hanley and Lippman-Hand 1983).

21.4 Design trade-offs

Decision Considerations
Test duration Longer tests find rarer problems but delay feedback
Logging detail More detail aids diagnosis but costs bandwidth, storage, energy and possibly privacy
Automated vs. manual testing Automation is repeatable and runs in CI; some field behavior can only be observed by people
Lab vs. field Labs are controlled and repeatable; the field is realistic

21.5 Common pitfalls

  • Testing only the happy path.
  • Logging only to the serial monitor, so the record disappears when the laptop sleeps.
  • No sequence numbers or timestamps, so loss and latency cannot be measured.
  • Changing firmware during a long test without restarting the clock.
  • Ignoring resets because “it came back”.
  • A demo that depends on unfamiliar Wi-Fi.
NoteAdvanced track

Statistics of rare failures. If your device runs 72 hours with no failures, what can you say about its mean time between failures? Using the “rule of three”, estimate a 95% upper bound on the failure rate, and discuss how many device-hours you would need to claim a mean time between failures of one year.

Chaos testing. Write a script that randomly disconnects the broker, delays messages and restarts the access point during a long test, and compare the system’s behavior with an undisturbed run.
